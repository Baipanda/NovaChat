# NovaChat 结合设计（修订）

## 结论

**聊天业务默认本地部署；RPC 用来拓展框架能力，并只服务「该远程」的调用。**

把用户/好友/消息全部打成 RPC 微服务，对当前体量并不合理：多一次序列化与网络往返，排错变难，也没有真实的独立扩容诉求。

## 合并后的形态

```text
客户端 JSON ──► Chat 节点（接入 + 业务 + MySQL Model）
                    │
                    ├── Redis Pub/Sub ──► 其他 Chat 节点推送
                    │
                    └──（按需）rpc ──► Presence / 附属服务 / 框架演示与压测
```

## 为什么聊天主路径不走 RPC

1. **调用形态不匹配**：发消息、改好友是节点内业务；推送靠长连接。RPC 是同步/异步请求-响应，不是推送总线。  
2. **数据与会话在一起更自然**：`_userConnMap`、登录态、紧接着的查库同进程完成，边界清晰。  
3. **过早拆分是负收益**：没有独立团队/独立扩容压力时，全量微服务主要增加运维与延迟。

## RPC 在本项目里的正当位置

| 用途 | 说明 |
|------|------|
| 框架本身 | Protobuf、自定义协议、Reactor、ZK、连接复用、压测 —— 这是后端深度 |
| 按需远程 | 例如跨节点 Presence/路由查询、后续独立扩的推送/文件等附属能力 |
| 面试叙事 | 「我知道什么该本地、什么该 RPC」，比「全拆了」更加分 |

## 调用链（主路径：本地）

1. Client → Chat 节点 `LOGIN_MSG` / `ONE_CHAT_MSG`  
2. `ChatService` 本地 `_userModel` / 好友 / 离线等  
3. 本机推送或 Redis 跨机推送  

## 调用链（按需：RPC 示例）

1. 需要知道用户在哪台节点时，Chat 节点 stub 调 `Presence.Query`  
2. 或压测/示例进程独立跑 `UserServiceRpc` demo，验证框架，而不强迫聊天主路径依赖它  

## 目录上的 `services/user|friend|message`

早期骨架按「全拆」搭过；**现行设计不再要求把这三块从 Chat 里拆走**。可保留为框架示例，或收成一个 `services/presence` / `example`，避免简历叙事和代码结构打架。
